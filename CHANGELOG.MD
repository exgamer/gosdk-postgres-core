# Changelog

## [1.5.0]

Зависимости: `gosdk-core` v1.3.0, `gosdk-db-core` v1.4.0.

Лок миграций на одном соединении, регистр без `(nil, nil)` после паники фабрики, TLS `prefer` и таймаут подключения
по умолчанию. Сигнатуры не изменились, новых переменных окружения нет.

### Исправлено

- `Migrator` (`Up`, `RollbackLast`, `RollbackTo`): `pg_advisory_lock` и `pg_advisory_unlock` шли на разных соединениях
  пула — лок мог не сниматься и висеть на простаивающем соединении, следующий накат ждал вечно. Теперь лок, миграции и
  снятие лока — на одном соединении (`db.Connection`); результат `pg_advisory_unlock` проверяется (не снят — ошибка);
  лок, занятый другой сессией, ждётся через `pg_try_advisory_lock` с повтором до 5 минут, затем ошибка.
- `PostgresGormRegistry.Get`: паника фабрики возвращала `(nil, nil)` — теперь `(nil, ошибка)`; фабрика, вернувшая
  `(nil, nil)`, — ошибка; соединение, созданное во время `CloseAll`, закрывается и не отдаётся (`(nil, ошибка)`).
- Пустой `POSTGRES_DB_SSLMODE` давал `sslmode=disable` — теперь `prefer`: TLS, если сервер его поддерживает, иначе
  без TLS. WARN при `APP_ENV` не `local` остаётся (режим в сообщении — `prefer`).
- В DSN добавлен `connect_timeout=5`, если в окружении нет `PGCONNECT_TIMEOUT`: недоступный хост больше не держит
  подключение до таймаута TCP ОС.

### ⚠️ Изменения поведения

- Пустой `POSTGRES_DB_SSLMODE` — `prefer`: с сервером, у которого включён TLS, соединение теперь шифруется (сертификат
  не проверяется — для проверки `verify-full`). Сервер без TLS — подключение как раньше. Нужен прежний режим —
  `POSTGRES_DB_SSLMODE=disable`.
- Подключение к БД, которая не отвечает дольше 5 с, — ошибка (раньше — ожидание таймаута ОС). Длиннее —
  `PGCONNECT_TIMEOUT`.
- Накат миграций, пока лок держит другой процесс дольше 5 минут, — ошибка `acquire migration lock: held by another
  session…` (раньше — ожидание без предела).
- С `gosdk-db-core` v1.4.0 (поднимается отдельно) пул без `POSTGRES_DB_MAX_OPEN_CONNECTIONS` ограничен 25
  соединениями.
- Тестовая зависимость `github.com/DATA-DOG/go-sqlmock` v1.5.2 в `go.mod`.

## [1.4.0]

Пароль БД не попадает в вывод конфига, предупреждение о соединении без TLS. Сигнатуры, переменные окружения и DSN не
изменились.

### Исправлено

- `config.PostgresDbConfig` выводился с паролем: `fmt` (`%v`, `%+v`, `%#v`) и `json.Marshal` (значения и указателя)
  теперь показывают `***` вместо непустого пароля (методы `String`, `GoString`, `MarshalJSON`). Поле `Password` -
  по-прежнему `string`, загрузка из окружения и `.env` не изменилась.

### Добавлено

- `helpers.WarnSslMode` - при `POSTGRES_DB_SSLMODE` `disable`, `allow`, `prefer` (и пустом) и `APP_ENV` не `local`
  (пустой и неизвестный - не `local`) один WARN: соединение может быть без шифрования. Вызывается при старте
  `PostgresKernel` и в `InitPostgresGormConnection`. Подключение - как раньше.

### ⚠️ Изменения поведения

- `json.Marshal(PostgresDbConfig)` отдаёт `"POSTGRES_DB_PASSWORD":"***"`: если конфиг сериализовали, чтобы передать
  дальше с паролем, - передавать поле `Password` явно.
- Методы `String`, `GoString`, `MarshalJSON` продвигаются в структуру, которая встраивает `PostgresDbConfig`: её
  `json.Marshal` и `fmt` отдают только поля Postgres. Не встраивать конфиг - держать его полем с именем.

## [1.3.0]

TLS к Postgres и экранирование DSN. По умолчанию подключение как раньше (`sslmode=disable`).

### Добавлено

- `POSTGRES_DB_SSLMODE` (`config.PostgresDbConfig.SslMode`) - режим TLS libpq: `disable`, `allow`, `prefer`,
  `require`, `verify-ca`, `verify-full`; пусто - `disable`; неизвестное значение - ошибка `InitPostgresGormConnection`.

### Исправлено

- DSN: значения в кавычках с экранированием - пароль с пробелом, `'`, `\` или `=` больше не ломает строку
  подключения и не меняет параметры (раньше `password=a b` отрезал пароль, `\` пропадал).
- `DbConfig.SslMode: true` давал `sslmode=enable` - такого значения в libpq нет; теперь `require`.

### ⚠️ Изменения поведения

- Пустой `POSTGRES_DB_PASSWORD`: раньше DSN `password= dbname=app_db` разбирался как пароль `dbname=app_db` без
  имени БД, и сервер подключал БД с именем пользователя. Теперь пароль пустой (`password=''`, без подстановки
  `PGPASSWORD`/`.pgpass`), а `POSTGRES_DB_NAME` соблюдается - сервис с пустым паролем подключится к указанной БД.
- Пароль с `\`, который удваивали в обход прежнего разбора (`a\\b` вместо `a\b`), теперь передаётся как есть -
  такие пароли записывать без удвоения, иначе вход не пройдёт.

## [1.2.0]

Зависимость `gosdk-db-core` поднята до v1.2.0. API пакета не изменился.

### Изменено

- `gosdk-db-core` v1.1.0 → v1.2.0.

### ⚠️ Изменения поведения

- Из `gosdk-db-core` v1.2.0: на уровнях `LOG_LEVEL` info и выше запрос, прерванный отменой контекста (`context.Canceled` — клиент оборвал запрос), не пишется в лог GORM как ошибка. `context.DeadlineExceeded` и остальные ошибки пишутся как раньше; debug/trace — без изменений.

## [1.1.0]

Зависимости `gosdk-core` и `gosdk-db-core` подняты до v1.1.0. API пакета не изменился.

### Изменено

- `gosdk-core` v1.0.29 → v1.1.0, `gosdk-db-core` v1.0.22 → v1.1.0.

### ⚠️ Изменения поведения

- Требует `gosdk-core` v1.1.0: поднимать вместе с `gosdk-http-core` ≥ v1.2.0, иначе сервис теряет
  AppInfo (имя сервиса) в логах запросов и событиях Sentry. AppInfo читать через
  `context.GetAppInfoFromContext`.
- Логгер экранирует управляющие символы в сообщениях (многострочное сообщение - одна строка с `\n`),
  `logger.Dump` пишет значение одной строкой.

## [1.0.24]

Минимальная версия Go поднята до 1.27.3. API и поведение пакета не изменились.

### Изменено

- `go.mod`: `go 1.26.0` → `go 1.27.3`. Причина - уязвимости стандартной библиотеки go1.26.0
  (`govulncheck`), исправлены в новых версиях Go. На go1.27.3 `govulncheck` уязвимостей стандартной библиотеки не находит.
- `gosdk-core` v1.0.28 → v1.0.29, `gosdk-db-core` v1.0.21 → v1.0.22 (обе тоже `go 1.27.3`).

### ⚠️ Изменения поведения

- Потребителю нужен Go ≥ 1.27.3: после `go get` этой версии в его `go.mod` станет `go 1.27.3`.
  С `GOTOOLCHAIN=auto` toolchain скачается сам; с `GOTOOLCHAIN=local` на Go < 1.27.3 или в образе
  без доступа к `proxy.golang.org` сборка упадёт - образ сборки `golang:1.27.3`.

## [1.0.23]

`POSTGRES_DB_*` из переменных окружения процесса (Docker, k8s, `docker run -e`) читаются
и без `.env`. Типы, поля и сигнатуры не изменились.

### Исправлено

- У полей `config.PostgresDbConfig` есть `json`-теги с теми же именами, что `mapstructure`
  (`json:"POSTGRES_DB_HOST"` и т. д.). Без них `InitConfig` из `gosdk-core` находил переменную
  в окружении, но не мог положить её в поле: применялись только ключи, которые есть в `.env`.
  Требуется `gosdk-core` v1.0.27+ (уже в `go.mod`).

### ⚠️ Изменения поведения

- Переменная `POSTGRES_DB_*`, которой нет в `.env`, но которая задана в окружении процесса,
  теперь применяется (раньше молча игнорировалась, поле оставалось пустым). Если `.env` нет совсем,
  конфиг целиком берётся из окружения. Для ключей, которые есть в `.env`, окружение было главнее
  и раньше.
- Неверное число или флаг в окружении (`POSTGRES_DB_MAX_OPEN_CONNECTIONS=abc`,
  `POSTGRES_DB_LOGGING=yes`) - ошибка `InitPostgresDbConfig` с именем переменной, `PostgresKernel`
  и консоль не стартуют (раньше ошибки не было: значение игнорировалось, для ключей из `.env`
  viper только печатал сообщение в stdout).
- Пустая переменная в окружении (`POSTGRES_DB_PASSWORD=`) теперь перекрывает значение из `.env`
  пустой строкой / `0` / `false` (раньше бралось значение из `.env`). Не задавайте пустые
  `POSTGRES_DB_*` в окружении, если значение должно прийти из `.env`.
- `json.Marshal(PostgresDbConfig)` выдаёт ключи `POSTGRES_DB_*` вместо имён полей (`Host`, `Port`…).
  В SDK и `go-sdk-rest-template` конфиг в JSON не сериализуется.
- Затронуты все места, где конфиг читается через `InitPostgresDbConfig` / `InitConfig`:
  `app.PostgresKernel` (через `newPostgresRegistry`), консоль `go-sdk-rest-template`
  (`internal/console/app.go`) и сервисы, созданные `gosdk-generator` с kernel `postgres`.
